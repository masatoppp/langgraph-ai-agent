# LangGraphを利用したAIエージェント

LangGraphの`State`・`Node`・`Edge`・`Conditional Edge`を利用し、  
ユーザーの質問内容に応じてRAGまたはWeb検索を選択して回答するAIエージェントを構築しました。

これまでに作成した社内文書RAGとWeb検索の処理をLangGraph上で統合し、  
質問の振り分け、情報取得、回答生成、Reflectionによる回答評価までを1つのワークフローとして実装しています。

本Portfolioでは、RAGやWeb検索そのものの新規実装よりも、  
**複数の処理をNodeとして分離し、StateとConditional Edgeを利用してエージェント全体の処理フローを制御すること**を主な目的としています。

## 主な機能

- LangGraphによるワークフロー制御
- `AgentState`によるGraph全体の状態管理
- Route NodeによるRAG / Web検索の選択
- Conditional Edgeによる条件分岐
- 社内文書を想定したRAG
- Tavilyを利用したWeb検索
- Qwen3-4BによるローカルLLM実行
- 4bit量子化によるローカルGPU実行
- Reflectionによる回答評価
- `retry`時の再実行
- `iteration`による再実行回数の制御
- RAG回答時の参照元表示
- 回答不能時の定型応答

## 設計の目的

本エージェントでは、社内文書のように外部サービスへ送信したくない情報は、  
ローカル環境のRAGとQwen3-4Bで処理します。

一方、最新ニュースや外部サービス、技術動向など、  
社内文書だけでは回答できない一般情報についてはWeb検索を利用します。

これにより、

- 社内固有情報はローカル環境で処理する
- 外部の最新情報が必要な場合のみWeb検索を利用する

という役割分担を実装しています。

## 全体構成

```text
START
  ↓
route
  ↓
select_route
 ↙        ↘
rag        web
 ↘        ↙
   answer
     ↓
 reflection
     ↓
select_reflection
 ↙      ↓      ↘
retry   ok      end
 ↓      ↓        ↓
route   END      END
```

処理を1つの大きな関数にまとめるのではなく、  
Route、RAG、Web検索、回答生成、Reflectionを独立したNodeとして分離しています。

これにより各処理の役割が明確になり、  
処理の追加・変更や、問題発生時の切り分けを行いやすい構成としています。

## Stateによる状態管理

Graph全体で使用する情報は`AgentState`に保持します。

主なStateは以下です。

- `query`：ユーザーからの質問
- `route`：RAG / Webの判定結果
- `context`：RAGまたはWeb検索で取得した情報
- `answer`：LLMが生成した回答
- `reflection`：回答評価結果
- `iteration`：再生成回数
- `has_answer`：取得した情報から回答できたかどうか
- `sources`：RAGで参照した文書の出典

Stateは最終結果だけを保存するものではなく、  
**各Node間で情報を受け渡すGraph全体の共有状態**として使用しています。

各NodeはState全体を作り直すのではなく、

```python
return {
    "answer": answer
}
```

のように変更した項目だけを返し、LangGraphが現在のStateへ反映します。

## ローカルLLM

回答生成、Route判定、Reflectionには`Qwen3-4B`を使用しています。

モデルは4bit量子化し、ローカルGPU上で実行します。

当初はQwen3-1.7Bも検証しましたが、  
Route判定やReflection判定の安定性を考慮し、本PortfolioではQwen3-4Bを使用しています。

Route判定やReflectionでは短い出力、回答生成では比較的長い出力が必要になるため、  
生成処理では用途に応じて`max_new_tokens`を変更できる構成としています。

## Router設計

最初にRoute Nodeでユーザーの質問を確認し、  
RAGまたはWeb検索のどちらを使用するか判定します。

### RAGへ振り分ける例

- 社内制度
- 社内規定
- 社内手続き
- 有給休暇
- 勤怠
- 給与
- 福利厚生
- 社用PCの紛失・故障・盗難
- 情報システム部門や社内運用に関する質問

### Web検索へ振り分ける例

- 最新ニュース
- 現在発生している不具合
- 社外製品・サービス
- 技術動向
- インターネット上の最新情報が必要な質問

Route判定は単純なキーワード一致ではなく、  
Qwen3-4Bに質問内容を渡し、質問全体の意味から`rag`または`web`を選択させています。

そのため、

```text
「有給」という単語が含まれているか
```

といった固定的なルールだけでなく、  
表現の違いや言い換えを含めて判定できることを狙っています。

一方、LLMによるRoute判定には誤分類の可能性があるため、  
判定精度の向上は今後の改善点の1つです。

## RAGについて

`RAG_test_data`には、社内文書を想定したダミーデータを配置しています。

主なカテゴリは以下です。

- 人事
- 労務
- 総務
- 情報システム

文書読み込み時に以下の情報をメタデータとして保持します。

- ファイル名
- 保存場所

文書は`RecursiveCharacterTextSplitter`を使用し、

```python
chunk_size=500
chunk_overlap=100
```

で分割しています。

文書を適切な大きさのchunkに分割することで検索対象を細分化し、  
Overlapを持たせることで分割境界付近の情報が失われにくい構成としています。

Embeddingには`multilingual-e5-base`を使用しています。

役割は以下のように分離しています。

- `multilingual-e5-base`：質問と文書をベクトル化し、関連する文書を検索する
- `Qwen3-4B`：取得した文書をもとに最終回答を生成する

Retrieverでは`TopK=3`としています。

TopKを大きくすると関連情報の取りこぼしを減らせる一方、  
質問と関係の薄い文書までContextへ含まれる可能性があります。

今回は小規模なダミー文書群を対象としているため、  
検索結果の量とノイズのバランスを考えて3件としています。

## RAGの参照元表示

RAGで回答した場合は、回答とともに参照したファイル名と保存場所を表示します。

社内文書検索では回答内容だけでなく、  
**どの文書を根拠に回答したかをユーザー自身が確認できること**も重要と考えたためです。

LLMの回答に誤りがあった場合でも、  
利用者が元文書へ戻って確認できる構成としています。

`create_sample_data.ipynb`を実行することで、RAG用のダミーデータを再生成できます。

## RAGからWeb検索へ自動Fallbackしない理由

社内情報としてRAGへ振り分けた質問について、  
RAGに回答根拠が存在しない場合でも、自動的にWeb検索へ切り替えない設計としています。

これは、Web上の一般的な情報を会社固有の制度として回答してしまうことを防ぐためです。

例えば、社内の有給休暇申請方法についてRAGに情報が存在しない場合、  
Web上の一般的な有給休暇制度を検索して回答してしまうと、  
実際の社内手続きとは異なる内容を案内する可能性があります。

そのため、参照文書に回答根拠がない場合は、

> 参照した情報には、質問に該当する情報がありません。

と回答して処理を終了します。

## Web検索

Web検索にはTavilyを使用しています。

検索結果から以下の情報を取得し、ContextとしてAnswer Nodeへ渡します。

- タイトル
- URL
- 検索結果本文

取得件数は最大3件としています。

また、「最新」の情報を求める質問で古い検索結果が優先されにくくなるよう、  
検索クエリには現在日付を追加しています。

```python
current_date = datetime.now().strftime("%Y-%m-%d")
search_query = f"{state.query} 最新 {current_date}"
```

Web検索結果をそのままユーザーへ返すのではなく、  
RAGと同様にAnswer Nodeへ渡し、質問に対する回答として再構成します。

## Answer Node

RAGまたはWeb検索で取得した`context`とユーザーの質問をQwen3-4Bへ渡し、  
最終回答を生成します。

RetrieverやWeb検索が返す情報は、あくまで検索結果や文書断片であるため、  
Answer Nodeでユーザーが理解しやすい回答へ再構成します。

また、ハルシネーションを抑えるため、以下の制約をプロンプトに設定しています。

- 参考情報に記載された内容だけを使用する
- 参考情報から推測して情報を補完しない
- Web検索結果に存在しない事実を追加しない
- 質問に直接必要な情報だけを回答する
- 質問に直接答える情報がなければ回答不能とする

回答不能の場合は、

> 参照した情報には、質問に該当する情報がありません。

と回答します。

## Reflection

回答生成後、Reflection Nodeで回答内容を評価します。

以下の場合は`retry`と判定します。

- 参考情報にない内容が回答に含まれている
- 質問と関係のない内容が含まれている
- 回答内容に矛盾がある

問題がなければ`ok`として終了します。

`retry`の場合は`iteration`を1増やし、Route Nodeへ戻って再度処理を行います。

無限ループを避けるため、再生成は最大3回までとしています。

この上限は、回答精度だけでなく、

- 処理時間
- ローカルLLMの実行負荷
- 無限ループの防止

とのバランスを考えた制御です。

### 現在のReflectionの制約

現在のReflectionは、

```text
ok
```

または

```text
retry
```

のみを返すシンプルな構成です。

そのため、Reflectionで検出した具体的な問題点を次回の回答生成へ渡しているわけではありません。

現状は、

```text
問題を検出
    ↓
retry
    ↓
Route Nodeから再実行
```

という構成です。

より高度な構成にする場合は、Reflectionの評価理由をStateへ保持し、  
次回のAnswer Nodeへ渡すことで、前回の問題点を踏まえた再生成が可能になると考えています。

また、検索したContext自体に問題がある場合は、  
検索クエリの修正やRetrieverの再検索まで含めたReflectionも改善案として考えられます。

## 回答不能時の処理

Answer Nodeでは、生成された回答文から回答可能性を判定し、  
`has_answer`へ結果を保存します。

回答不能と判定された場合は、  
正しい「回答できない」という結果としてReflectionによる再生成を行わず、`ok`として終了します。

これにより、参照情報に存在しない内容を無理に生成し続けることを防いでいます。

## Node分割の目的

本エージェントでは以下の処理を独立したNodeとして実装しています。

- Route Node：RAG / Webの選択
- RAG Node：社内文書検索
- Web Node：外部情報検索
- Answer Node：回答生成
- Reflection Node：回答評価

Nodeごとに処理の責務を分離することで、  
1つの大きな関数へすべての処理をまとめる場合と比較して、

- 処理フローを確認しやすい
- 問題が発生したNodeを切り分けやすい
- 特定のNodeだけを修正しやすい
- 新しい処理を追加しやすい
- 条件分岐や再実行を表現しやすい

という利点があります。

Stateが「Node間で共有する情報」を管理するのに対し、  
NodeとEdgeは「処理の流れ」を管理する役割を持ちます。

## Graphの構築

`AgentState`を使用して`StateGraph`を作成し、  
各NodeとEdgeを登録した後にGraphをcompileします。

```python
workflow = StateGraph(AgentState)

workflow.add_node("route", route_node)
workflow.add_node("rag", rag_node)
workflow.add_node("web", web_node)
workflow.add_node("answer", answer_node)
workflow.add_node("reflection", reflection_node)
```

RouteとReflectionではConditional Edgeを使用し、  
Stateの値に応じて次の処理を変更します。

最後に、

```python
app = workflow.compile()
```

として実行可能なGraphを生成します。

## 今後の改善点

### 1. Route判定の改善

現在はQwen3-4Bが質問の意味からRAG / Webを判定しています。

キーワードルールより柔軟な判定が可能である一方、  
LLMによる誤分類の可能性は残ります。

今後は、RAG検索結果の類似度などを組み合わせ、  
LLMの判定だけに依存しないRoute構成も検討できます。

### 2. Reflection結果の再利用

現在はReflectionで`retry`となった場合も、  
具体的な評価理由を次回の回答生成へ渡していません。

評価理由をStateへ保持し、Answer Nodeへ渡すことで、  
前回の失敗内容を踏まえた再生成が可能になると考えています。

### 3. `has_answer`判定の改善

現在の`has_answer`は生成された回答文に含まれる特定の表現から判定しています。

そのため、回答可能性そのものを独立して判定しているわけではなく、  
誤判定する可能性があります。

回答生成とは別に回答可能性を判定するNodeを設けることも改善案として考えられます。

### 4. RAG検索の高度化

現在はベクトル検索のみを使用しています。

ベクトル検索は意味的な類似性に強い一方、  
固有名詞、制度名、製品名など文字列一致が重要な検索では弱くなる場合があります。

BM25などのキーワード検索と組み合わせたハイブリッド検索や、  
Re-Rankの導入も改善案として考えられます。

### 5. Web検索品質の改善

Web検索結果の鮮度や本文抽出品質によって回答精度が左右されます。

今後は、

- 検索結果の関連性
- 取得期間
- 情報源
- 検索クエリ

などをより厳密に制御する余地があります。

### 6. 会話履歴への対応

現在は1回の質問に対して、

```text
Route
↓
検索
↓
回答
↓
Reflection
```

を行う単発の質問応答型です。

今後はStateに会話履歴を保持し、

```text
ユーザー:
有給休暇の申請方法は？

AI:
...

ユーザー:
では半休の場合は？
```

のような、前の回答を前提とした追加質問へ対応できる構成を検討しています。

Stateに`messages`などの履歴を保持することで、  
より実用的な対話型社内エージェントへ拡張できると考えています。

## 本Portfolioで工夫した点

特に意識した点は、  
**ローカルLLMを中心とした閉じた処理とWeb検索を1つのエージェント内で使い分けたこと**です。

社内文書に関する質問はRAGとローカルLLMで処理し、  
社内固有情報をWeb検索へ自動的にFallbackしない構成としました。

一方で、最新ニュースや外部サービスなど、  
一般的な外部情報が必要な質問についてはWeb検索を利用します。

「社内情報は外部へ問い合わせたくないが、必要に応じて一般的な最新情報も取得したい」

という利用場面を想定し、  
LangGraphのRouteとConditional Edgeを利用して処理を分離しています。

## 補足

本Portfolioでは、RAGやWeb検索そのものを新規に作ることよりも、  
既存の処理をLangGraph上でNodeとして接続し、  
StateとConditional Edgeによってワークフロー全体を制御することを主な目的としています。

RAG、Web検索、回答生成、Reflectionをそれぞれ独立したNodeとして扱うことで、  
処理の責務を分離しながら、条件分岐と再実行を含むAIエージェントを実装しました。
